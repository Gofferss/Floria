## 1. `app/api/orders/route.ts` — создание заказа ✅

Принимает `CheckoutPayload` (тип определён в `lib/checkout.ts`, форма
`/checkout` собирает данные именно в этом формате — маппинг 1:1 на поля
таблицы `orders` из Шага 1).

Реализованные шаги внутри route handler:
1. Валидация payload на сервере (не доверяем клиентской валидации).
2. Пересчёт `itemsTotal`, `deliveryPrice`, `bonusUsed`, `totalAmount` на сервере — клиентские цифры используются только для UI-превью, не для записи в БД.
3. Генерация `order_number` (`FL-` + время в base36 + случайный суффикс).
4. Вызов мока Posiflora (`lib/posiflora.ts`) — получаем `posiflora_order_id` и `bonus_earned` (условные 5% от суммы товаров). При сбое интеграции заказ всё равно создаётся, но без `posiflora_order_id` — менеджер обработает вручную.
5. `insert` в `orders`, затем `insert` в `order_items` (`service_role` ключ Supabase через `getSupabaseAdmin()`, только на сервере).
6. Fire-and-forget POST на вебхук n8n.
7. Ответ клиенту: `{ orderId, orderNumber, totalAmount }`.

Оплата (шаг 5 из первоначального плана) в этом шаге сознательно не подключена — см. план ниже.

## 2. Алерты о новых заказах в Telegram — через n8n ✅

В проекте уже подключён MCP-коннектор n8n, поэтому вместо написания
отдельного Telegram-бота логичнее использовать готовый **Webhook-триггер
n8n → Telegram-нода**:

1. В n8n создаётся workflow с узлом **Webhook** (например, `/webhook/floria-new-order`).
2. Route handler `/api/orders` при успешном создании заказа делает `fetch` на URL этого вебхука (переменная окружения `N8N_ORDER_WEBHOOK_URL`), передавая: номер заказа, сумму, получателя, адрес, время доставки, ссылку на заказ в админке.
3. В workflow n8n узел **Telegram (Send Message)** форматирует сообщение и отправляет в рабочий чат/канал студии.
4. Аналогично можно завести второй webhook-алерт на событие "заказ оплачен" (после вебхука Т-Pay/СБП) — отдельным узлом или веткой в том же workflow, чтобы отличать "новый заказ" от "оплаченный заказ".

Такой подход не требует хранить токен Telegram-бота в коде фронтенда/бэкенда
Floria — он остаётся внутри n8n.

## 3. Обработка оплаты — план на следующий шаг ⏳

- `app/api/payments/webhook/route.ts` — принимает колбэк от Т-Pay/СБП, проверяет подпись, обновляет `orders.payment_status` и `orders.paid_at` в Supabase.
- При успешной оплате: финализировать списание/начисление бонусов в Posiflora (до этого момента бонусы можно резервировать, но не списывать окончательно).
- На `/checkout` кнопка «Перейти к оплате» сейчас создаёт заказ со статусом `payment_status = 'pending'` и сразу показывает экран успеха — редирект на страницу оплаты Т-Pay/СБП подключится, когда появится сам платёжный шлюз.

## Переменные окружения (появятся на Шаге 5)

| Переменная | Назначение |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | URL проекта Supabase (клиент, публичный) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon-ключ (клиент, публичный) |
| `SUPABASE_SERVICE_ROLE_KEY` | service-role ключ — только сервер, `app/api/**` |
| `POSIFLORA_API_KEY` / `POSIFLORA_API_URL` | доступ к API кассы Posiflora |
| `TPAY_SECRET_KEY` | приём платежей Т-Pay |
| `SBP_MERCHANT_ID` | приём платежей через СБП |
| `N8N_ORDER_WEBHOOK_URL` | webhook n8n для алертов "новый заказ" |
| `N8N_PAYMENT_WEBHOOK_URL` | webhook n8n для алертов "заказ оплачен" |

## Что уже готово на фронтенде под это

- `lib/checkout.ts` → тип `CheckoutPayload` — ровно то тело запроса, которое принимает `POST /api/orders`.
- `CheckoutView.tsx` строит этот payload при сабмите и отправляет его реальным `fetch("/api/orders", ...)`; при ошибке показывает баннер и возвращает форму, при успехе — очищает корзину (`useCart().clear()`) и показывает экран с номером заказа, пришедшим от сервера.
- `components/cart/CartProvider.tsx` — после интеграции оплаты можно оставить как есть (для гостей без аккаунта) или синхронизировать с серверной корзиной для авторизованных пользователей.
