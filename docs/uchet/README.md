# Флория Учёт

Своя система учёта студии вместо Posiflora: склад, витрина, заказы из
магазина, смены и деньги, сотрудники, отчёты. Живёт в том же приложении и
той же базе, что сайт, — это и есть главная причина её делать.

Документ для разработчика. Владельцу — проектный документ
<https://claude.ai/artifact/1m1Nxq6nUdSkkxc4jGUABE>.

---

## Зачем

Posiflora не умеет связать состав букета с заказом. Для цветочной студии
это главный предмет учёта, и из-за этого ограничения:

- состав заказа с сайта уходил в кассу текстом в комментарии;
- сумма заказа с сайта в Posiflora всегда 0 ₽ (считается по позициям, а
  позиций через API не привязать);
- онлайн-оплату она не видит;
- остатки сайт вынужден спрашивать у чужой программы раз в 15 минут.

Плюс данные показали, что закупка цветов в Posiflora записывается как
изъятие денег из кассы (причины «Эустома», «Хризантема», «Георгины
купила»), а приходов на склад за всё время 12. Остатки и себестоимость там
поэтому неточны.

## Решения владельца (21.10.2026)

| Вопрос | Решение |
|---|---|
| Устройства | Один iPad, в загруженные дни два. Курьеру — свой доступ с телефона: его заказы, адреса, статусы |
| Точки | Одна. «СКЛАД» в Posiflora был тренировочным, перемещений нет |
| Закупка | «По-разному»: поставщик и способ оплаты — необязательные поля |
| Оплата сотрудникам | Настраивается на человека: «5% от продаж + фикс 50 000», «5 500 за смену» и т. п. |
| Кто видит себестоимость и прибыль | Только владельцы — роли `owner` и `admin` |
| Чеки | Бьются отдельной кассой. Система только для внутреннего учёта, фискализации нет |
| Бонусы | 5% |
| Доступы (22.10.2026) | Вход — у человека или устройства, не «у роли»: владельцам личные, айпаду магазина общий с ролью florist, курьеру свой. Люди за общим айпадом различаются PIN |
| Вид (22.10.2026) | Спокойный: цвет только у того, что требует внимания. Группы различаются значком |

**Posiflora не трогаем:** ничего в ней не удаляем и не архивируем. Только
читаем. Существующая отправка оплаченных заказов с сайта
(`lib/posiflora/push-order.ts`) остаётся до перехода.

## Принципы

### 1. Остаток не хранится — он считается

Склад — это журнал документов. Каждый документ — набор строк «позиция,
изменение количества, цена». Остаток позиции = сумма изменений по
проведённым документам.

Таблица `inv_stock` — только кэш этой суммы, её пишет одна функция
проведения. Представление `inv_stock_check` сравнивает кэш с журналом и
должно быть пустым; если в нём есть строки — что-то записало остаток в
обход журнала, и это ошибка.

Отсюда же работа без интернета: планшет только дописывает документы, а не
правит числа, поэтому два устройства не могут затереть друг другу остаток.

### 2. Проведённое не правится

Строки проведённого документа менять и удалять нельзя — это запрещено
триггером в базе, а не договорённостью. Ошибку исправляют сторно: новый
документ с теми же строками и обратным знаком (`inv_reverse_document`).
Всегда видно, кто, когда и что сделал.

### 3. Себестоимость — скользящая средняя

При каждом приходе средняя цена позиции пересчитывается:
`(остаток × средняя + пришло × цена) / (остаток + пришло)`. Расход
(списание, продажа, сборка) замораживает в строке ту среднюю, что была в
момент проведения. Поэтому прибыль за прошлый месяц не меняется от
сегодняшних закупок.

Отрицательный остаток в среднюю не входит: считается от
`greatest(остаток, 0)`.

### 4. Продажу не блокируем ради цифры

Если остаток ушёл в минус — продажа всё равно проходит, а владелец
получает тревогу. Клиент уже стоит у прилавка; ошибку в учёте исправляют
инвентаризацией, а не отказом продать.

### 5. Правила — в настройки, не в код

Если правило формулируется одной фразой («флорист даёт скидку до 10%»,
«напомнить закрыть смену в 21:30»), оно должно настраиваться в админке.
Причины списаний, группы, единицы, поставщики, схемы оплаты сотрудников,
пороги тревог — данные, а не константы.

### 6. Права — в базе и на сервере, не в интерфейсе

Все таблицы учёта закрыты RLS без политик и без грантов для `anon` и
`authenticated`: читать и писать их может только сервер ключом
service-role. Функции явно лишены `EXECUTE` для `public` — по умолчанию
PostgreSQL выдаёт его всем, и через PostgREST любую функцию можно было бы
вызвать анонимно. Подробнее о том, почему одного RLS мало, — в истории
дыры с бонусами (миграция 015).

Роль учётной записи проверяется и на странице, и в каждом серверном
действии (`lib/auth/roles.ts`, `requireStaffUser` / `requireStaffAction`):
скрытая кнопка не мешает вызвать действие напрямую.

| Роль | Что открыто |
|---|---|
| `owner`, `admin` | Всё: учёт, деньги, себестоимость, сотрудники, админка сайта |
| `manager` | Админка сайта и рабочие разделы учёта, без себестоимости |
| `florist` | Касса, витрина, склад, смена; из админки сайта — только заказы |
| `courier` | Только «Доставки» |

### 7. Кто сделал — человек, а не учётная запись

Айпад магазина входит одной учётной записью. Человек за ним выбирает себя
и вводит PIN (`lib/uchet/employee.ts`): сервер ставит подписанную куку
«сотрудник N на этой учётной записи до такого-то часа». Каждый документ,
продажа и движение наличных несут `employee_id`. Если на общей учётной
записи человек не выбран, а люди с PIN заведены, — действие не
выполняется. PIN хранится scrypt-хэшем, после 5 ошибок — пауза 5 минут.
Скидку сверх лимита подтверждает PIN того, у кого `can_approve`: сервер
выдаёт подписанный допуск на 15 минут, сам PIN в браузере не остаётся.

## Модель данных

Префикс `inv_` — склад. Дальше по этапам добавятся `pos_` (продажи,
смены, деньги) и `hr_` (сотрудники, оплата).

### Этап 1 — склад (миграция 024)

| Таблица | Что хранит |
|---|---|
| `inv_units` | Единицы: штука, ветка, пучок, метр, лист, кг, упаковка |
| `inv_groups` | Группы позиций, двухуровневые (`parent_id`): «Цветы → Розы» |
| `inv_locations` | Места хранения. Сейчас одно — «Магазин» |
| `inv_suppliers` | Поставщики |
| `inv_writeoff_reasons` | Причины списания — редактируются владельцем |
| `inv_items` | Позиции: название, группа, единица, цена продажи, минимум, срок свежести, кэш средней себестоимости |
| `inv_documents` | Документы: начальный остаток, приход, списание, инвентаризация (дальше — сборка, продажа, возврат) |
| `inv_document_lines` | Строки документов — это и есть журнал движений |
| `inv_stock` | Кэш остатков (позиция × место) |
| `inv_doc_counters` | Счётчики номеров документов по типам |
| `inv_posiflora_snapshot` | Последний снимок остатков Posiflora — для сверки во время параллельной работы |

| Функция / представление | Что делает |
|---|---|
| `inv_post_document(doc, staff)` | Проводит черновик атомарно: считает изменения, морозит цены, пишет кэш |
| `inv_reverse_document(doc, staff, comment)` | Сторно проведённого документа |
| `inv_item_freshness` | Возраст самой старой партии в остатке (FIFO) — «эустоме шестой день» |
| `inv_stock_check` | Расхождения кэша с журналом. Должно быть пусто |

Типы документов и знак изменения:

| Тип | Номер | Изменение остатка | Цена в строке |
|---|---|---|---|
| `opening` — начальный остаток | НО-0001 | + количество | введённая, иначе текущая средняя |
| `receipt` — приход (закупка) | ПР-0001 | + количество | цена закупки, обязательна |
| `writeoff` — списание | СП-0001 | − количество | средняя на момент проведения |
| `inventory` — инвентаризация | ИН-0001 | насчитано − было по учёту | средняя на момент проведения |

### Этап 2 — торговый зал (миграция 028)

| Таблица | Что хранит |
|---|---|
| `hr_employees` | Люди за планшетом: имя, должность, PIN (хэш), «подтверждает скидки», личный вход |
| `pos_settings` | Правила кассы: лимит скидки, «состав обязателен», бонусы включены |
| `pos_payment_methods` | Способы оплаты (наличные считаются в кассе) |
| `pos_cash_reasons` | Причины внесения и изъятия; вид: закупка, зарплата, инкассация, другое |
| `pos_shifts` | Смены: открытие, ожидаемое и насчитанное при закрытии. Открытая — одна на место |
| `pos_cash_movements` | Внесения и изъятия. Не правятся; закупка связана с приходом на склад |
| `pos_bouquets`, `pos_bouquet_items` | Каждый собранный букет с составом: витрина, продан, разобран, списан |
| `pos_sales`, `pos_sale_lines`, `pos_payments` | Чеки: строки трёх видов (букет, витрина, позиция) и оплаты |

| Функция | Что делает |
|---|---|
| `pos_open_shift`, `pos_close_shift`, `pos_cash_move` | Смена и наличные; закрытие считает расхождение |
| `pos_shift_expected_cash` | Открытие + наличные оплаты + внесения − изъятия |
| `pos_assemble_bouquet` | Букет на витрину: документ сборки списывает состав сразу |
| `pos_disassemble_bouquet` | Разборка: цветы обратно по цене сборки |
| `pos_writeoff_bouquet` | Списание завявшего букета — без движения склада |
| `pos_record_sale` | Продажа одной транзакцией: чек, строки, оплаты, букеты, документ продажи. Идемпотентна по id |

Новые типы документов склада: `assembly` (СБ) и `sale` (ПД) списывают по
средней, `disassembly` (РЗ) и `return` (ВЗ) приходуют по переданной
цене. Через `inv_reverse_document` они не сторнируются — продажу отменяет
возврат, сборку — разборка. Свежесть их приход не считает новой партией.

Бонусы пока ведёт Posiflora (`customers.bonus_balance` — её баланс):
касса их показывает, но не списывает и не начисляет, пока
`pos_settings.bonuses_enabled` выключено.

### Заказы магазина (миграция 029)

Заказ из зала, по телефону или из мессенджера — `pos_orders`, отдельно от
`orders` сайта: владелец решил, что по заказам магазина клиенту в бот не
пишут, а к `orders` привязаны уведомления, отзывы и личный кабинет.

- **Оплата — продажи.** Предоплата, доплата и остаток — чеки со строкой
  вида `order` (`pos_record_sale`), по одному заказу на чек и без скидки.
  Оплачено = сумма таких строк в невозвращённых чеках (`pos_order_paid`).
  Переплатить нельзя: заказ блокируется на время оплаты.
- **Сборка к заказу** — `pos_assemble_bouquet` с `order_id`: состав
  списывается сразу, букет в статусе `order`, заказ становится «собран».
  Можно и «собран без состава» — как букет по цене.
- **Шаги** — `pos_set_order_status`, только вперёд: новый → собирается →
  собран → у курьера → доставлен; самовывоз — собран → выдан. При выдаче
  букеты к заказу становятся проданными; склад и касса не трогаются.
- **Отмена** — `pos_cancel_order`: с предоплатой нужно выбрать — вернуть
  наличными (изъятие в открытой смене), вернули картой или переводом (мимо
  кассы) или оставить у студии. В первых двух случаях чеки предоплаты
  помечаются возвратом. Собранные букеты переезжают на витрину.
- **Наличные в кассе** считаются по всем чекам смены, включая
  возвращённые: возврат наличными — отдельное изъятие, иначе он вычитался
  бы дважды.

### Маршруты доставки (миграция 030)

Обычно курьер один, в праздники — два-три (8 марта ~40 доставок). У
доставки — точка на карте, курьер (вход с ролью courier) и номер
остановки. План — экран «Доставки» в учёте.

- **Адрес → точка** — DaData (`lib/geo/dadata.ts`, ключ `DADATA_API_KEY`
  в Coolify). Бесплатно 10 000 запросов в день; координаты отдаются только
  на запрос с count = 1. Ответы кэшируются в `geo_cache`, найденная точка
  пишется в сам заказ. Уходит только адрес. Без ключа всё работает, но
  порядок строится только по времени. Для половины домов вне Москвы у
  DaData точка — по улице (qc_geo ≥ 2), это показывается в плане.
- **Раскладка по курьерам** — «веером» от студии (`splitByCouriers`):
  сектора поровну, разрез по самому широкому пустому промежутку.
- **Порядок** — `orderRoute`: окна времени по очереди, внутри окна —
  ближайший адрес; «в течение дня» — вставкой с наименьшим крюком.
  Расстояния по прямой; дорогу ведёт Яндекс Навигатор.
- **Ссылки** — Яндекс Карты, `rtext=lat,lon~lat,lon&rtt=auto` (формат из
  документации Яндекса). Лимит точек Яндекс не публикует — режем по 9.
  У курьера маршрут — от текущего места (пустая первая точка).
- Проверка расчёта — на 40 случайных адресах (поровну, сектора без чужих
  адресов, окна по порядку, путь короче «просто по времени» на 15–30%).

### Сводка для владельцев (миграция 031)

Экран `/uchet/svodka`, только владельцы. Код — `lib/uchet/summary.ts`.

- **Откуда цифры.** Posiflora — готовой статистикой (`/stats/stores/*`,
  только GET, кэш в памяти: 3 минуты для периода с сегодняшним днём,
  30 — для прошлого). Учёт — с даты `pos_settings.summary_uchet_since`;
  до неё наши чеки показываются строкой «для сверки», но не складываются
  с Posiflora: в месяц параллельной работы продажа бьётся в обеих кассах.
  Сайт — заказы с онлайн-оплатой; в Posiflora их сумма 0, дублей нет.
- **Порог дохода за год** (`INCOME_LIMIT_BY_YEAR`, на 2026 — 20 млн ₽):
  доход = поступления Posiflora (`paymentsRevenue`, доход на УСН — по
  оплатам) + Учёт + сайт + «вне систем» (`summary_income_extra`, в 2026 —
  январь–март: история Posiflora с апреля). Прогноз — по темпу последних
  90 дней. Показывается дата превышения и с какого числа НДС (1-е число
  следующего месяца).
- **Способы оплаты Posiflora** подписывает владелец
  (`pos_settings.posiflora_payment_names`): API отдаёт доли по способам,
  а сами способы — нет (`/payment-methods` — 500, `include` — 422/500).
- **Прибыль** — из Posiflora и только как ориентир: закупка там шла
  изъятием из кассы, поэтому себестоимость неточная. По Учёту прибыль
  появится, когда закупка пойдёт приходом.
- Если Posiflora не ответила, блок так и пишет — не нулями.

### Зарплата (миграция 032)

Экран `/uchet/lyudi/zarplata`, только владельцы. Код — `lib/uchet/payroll.ts`.

- **Схема** — набор частей на человека (`hr_pay_rules`): оклад в месяц,
  за смену, процент от продаж (своих / точки в его дни / всей точки), за
  букет, за доставку. Меняется «с даты» функцией `hr_set_pay_scheme`:
  действующие части закрываются накануне, прошлые месяцы считаются по
  старым правилам. Оклад при смене схемы внутри месяца — по дням.
- **Рабочие дни.** До перехода на Учёт — по сменам Posiflora: кто открыл
  или закрыл смену. Второго флориста в загруженный день смена не знает,
  его отмечают в табеле. После запуска — вход по PIN (`markWorkDay` в
  `lib/uchet/employee.ts`, только когда основное место не «Тренировка»).
  Ручная отметка (`hr_work_days`, source manual) перекрывает и то и другое.
- **Продажи** — по той же дате перехода, что и сводка: личные — из
  `stats/workers` Posiflora (человек связан через
  `hr_employees.posiflora_worker_id`) или из чеков Учёта по `employee_id`.
- **Выдачи** — из кассы Учёта (изъятие «Зарплата» с `paid_employee_id`)
  сами; мимо кассы — `hr_payouts`. Суммы выдач из кассы Posiflora её API не
  отдаёт (причины «Зарплата Даня», «Зарплата Таня» есть, операций нет) —
  до запуска их вписывают руками.
- **Осталось выдать** — накопительно с первого месяца, где есть схема,
  премия или выдача (не дальше 12 месяцев назад).
- Проверено на настоящих сменах и продажах Posiflora за октябрь 2026 с
  примерными схемами: 8 расчётов сошлись с ручным пересчётом.

### Настройки

Экран `/uchet/nastroiki`, только владельцы (`lib/uchet/settings-actions.ts`):
скидка без подтверждения, можно ли продать букет без состава (выключено —
касса прячет «Букет по цене», база и так не пропустит), способы оплаты и
причины внесения/изъятия. Удаления нет — только выключение. Нельзя:
выключить «Наличные», сменить «наличные или нет» у способа, которым уже
платили (пересчитало бы прошлые смены), сменить смысл причины и выключить
последнюю причину служебного смысла (закупка, зарплата, инкассация,
возврат). Бонусы показаны, но не включаются — их ведёт Posiflora.

### Клиенты

Экран `/uchet/klienty`, только владельцы (`lib/uchet/customers.ts`). База
одна с сайтом — `customers`, ключ — телефон `+7XXXXXXXXXX`. Покупки: заказы
сайта (оплаченные или выполненные), чеки кассы и заказы магазина на
настоящих местах (чеки «Тренировки» не считаются). Касса заводит клиента
по полному номеру (`createCustomerAtTill`) — ТОЛЬКО у нас, без Posiflora,
иначе пробы в «Тренировке» засорили бы её; связь с Posiflora появится
сама, когда человек закажет на сайте или войдёт. На 21.10.2026 в Posiflora
всего 14 клиентов (продажи там почти все анонимные) — недостающих
переносит кнопка на экране, в Posiflora при этом ничего не пишется.

### Продажа без связи

Если связь пропала в момент оплаты, чек не теряется: касса кладёт его в
очередь на айпаде (`components/uchet/kassa/outbox.ts`, localStorage
`uchet.outbox.v1`) и показывает «Сохранено — уйдёт само». Значок в шапке
учёта (`OutboxStatus`) досылает очередь при открытии, при появлении связи и
раз в 20 секунд. Повтор безопасен: `pos_record_sale` проводит чек по его id
один раз. Причины сбоя различаются (`classifyFailure`): нет связи —
досылаем; старая версия страницы после выкладки — просим обновить;
сервер ответил ошибкой (истёк вход, смена закрыта, букет уже продан) —
«Не прошло» с причиной и кнопками «Повторить» / «Убрать». Пока очередь не
пуста, смену не закрыть: пересчёт кассы не сойдётся. Проданные без связи
букеты витрины второй раз не предлагаются. Не умеет: открыть учёт с нуля
без связи и провести без связи что-то кроме продажи. Продажа уходит от
имени того, кто выбран на айпаде в момент досылки, и со временем досылки.

Проверено в браузере с подменённой сетью: продажа ложится в очередь, при
возврате связи уходит; отказ сервера — в «Не прошло», а не в вечную очередь.

### Деньги

Экран `/uchet/dengi`, только владельцы (`lib/uchet/money.ts`), за месяц, по
той же дате перехода, что сводка. Главное — расхождения по сменам: при
открытии (не то, что оставили в прошлый раз) и при закрытии (насчитали не
столько, сколько должно быть). У смен Posiflora это поля
`openingAmountDiff` и `variance`; у нас — `opening_cash −
previous_counted_cash` и `counted_cash − expected_cash`. Итог — одной
суммой со знаком: опечатка при открытии даёт пару «минус при открытии,
плюс при закрытии». В Posiflora часто две смены в день — вторую владелец
открывает вечером для изъятия. Выдачи из кассы Posiflora через API не
читаются — до перехода раздел выдач пуст.

### Дальше (эскиз, уточняется по ходу)

- **Рецепты** — уже есть: `product_recipe_items`. Переводятся с позиций
  Posiflora на `inv_items`.
- **Букеты витрины** — `pos_bouquets`: экземпляр собранного букета со
  статусом «собран → на витрине → забронирован → продан / списан», фото,
  фактическим составом и ценой. Сборка — документ `assembly`, списывающий
  компоненты.
- **Резерв** — `inv_reservations`: уменьшает «доступно», не трогая остаток.
- **Продажи и заказы магазина** — расширение `orders` (источник «магазин»)
  и документ `sale`.
- **Смены и деньги** — `pos_shifts`, `pos_cash_movements` (внесение,
  изъятие, закупка из кассы, зарплата), способы оплаты.
- **Сотрудники** — PIN для планшета, журнал действий, схемы оплаты
  `hr_pay_rules`: оклад, ставка за смену, процент от продаж (личных, за
  смены, всей точки), за букет — и их сочетания.
- **Курьер** — роль `courier`: свои заказы, адреса, статусы.
- **Офлайн** — планшет как PWA с экрана «Домой», локальная база (IndexedDB),
  очередь документов с UUID, создаваемыми на устройстве; сервер принимает
  повтор идемпотентно.

## Как работать

**Миграции** лежат в `migrations/`. SSH к серверу нет; миграция
применяется разовой задачей Coolify в контейнере `supabase-db`, которая
скачивает файл с GitHub по закреплённому коммиту и передаёт в `psql`.
Задачу после запуска удалить. Подробности — в памяти проекта
(«Infra access»).

**Импорт из Posiflora** — `scripts/uchet-import-posiflora.mjs`. Только
читает Posiflora, повторный запуск ничего не задваивает (сопоставление по
`posiflora_id`).

**Тесты** — `migrations/tests/024_warehouse_core_test.sql`,
`026_save_draft_test.sql`, `028_shop_floor_test.sql`, `029_shop_orders_test.sql`, `031_owner_summary_test.sql`, `032_payroll_test.sql`. Выполняются внутри
транзакции с `ROLLBACK` в конце, поэтому ничего не оставляют в базе;
каждое расхождение — `RAISE EXCEPTION`.

Новую миграцию сначала прогоняют «насухо»: миграция и все тесты в одной
транзакции с откатом (`migrations/tests/028_dryrun.sql` — так проверялись
новые версии функций проведения на старых тестах склада), и только потом
применяют.
